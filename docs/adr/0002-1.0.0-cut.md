# ADR 0002 — 1.0.0 cut

- **Status:** Accepted
- **Date:** 2026-05-28
- **Deciders:** radimsem (skill owner)

## Context

The five-phase redesign tracked in [`../specs/2026-05-28-forge-redesign.md`](../specs/2026-05-28-forge-redesign.md) reached Phase 5 + a polish PR in a single session. The spec's §9 versioning policy said "1.0.0 cuts after Phase 5 soaks" — implying a calendar gap between 0.6.0 and 1.0.0 for real-world use to surface issues.

The user (skill owner) elected to cut 1.0.0 in the same session rather than wait for a calendar-defined soak. This ADR records the decision so future contributors understand why 1.0.0 ships without a calendar soak window.

## Decision

Cut 1.0.0 immediately on completion of Phase 5 + polish. Soak time is deferred to real-world use rather than enforced by a calendar gap.

## Rationale

- The Phase 5 deltas are additive (one new reviewer flag + rework path); no existing semantics changed. Risk surface is the new flag's interactions, all of which are already documented in `references/reviewers/coderabbit.md` and the autonomy matrix.
- The polish PR fixed the only known regression (the 0.6.0/README.md path-tracking miss in PR 5c) and split the anti-patterns table per the spec's planned escape.
- All 13 planned flags ship; the surface area is now what the spec promised. Holding 1.0.0 back for a calendar reason would not change what's in 1.0.0 — it would only delay the stability promise.
- Post-1.0 contracts (flag rename = major bump, new flag = minor bump, doc-only = patch) are documented in `1.0.0/README.md` so downstream users can rely on SemVer guarantees from day one.

## Alternatives considered

1. **Calendar soak (1 week between 0.6.0 and 1.0.0).** Conservative; would have caught any unknown-unknown issues from real use. Rejected because there's no calendar pressure to ship 1.0.0 quickly, and `0.6.0` remains in the repo for rollback if 1.0.0 develops issues.
2. **Skip 1.0.0; ship as 0.7.0+.** Less commitment to SemVer stability. Rejected because the redesign is genuinely done — calling it 0.7.0 would imply more changes were planned, which is not the case.

## Consequences

**Positive:**
- The stability promise begins immediately; downstream users can pin to `^1.0.0` and rely on no breaking changes within the major.
- The five-phase redesign has a clean termination — `1.0.0/` is the canonical version, every prior `0.x.y/` is historical.

**Negative:**
- Any latent bug discovered post-cut requires either a 1.0.1 patch (if non-breaking) or a 2.0.0 (if breaking). The first patch release is the canary; if no real-world issues surface within ~30 days of use, the 1.0.0 cut decision is validated retroactively.
- The "soak" concept from spec §9 was meaningful in principle but was not enforceable in this single-session implementation. Future major-version cuts (2.0.0+) should consider whether a real calendar soak is warranted.
